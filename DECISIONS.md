# Decisions log

Rulings that fix boundaries between Nook tasks. Builders and the arbiter read this before working. Append, never rewrite.

## Settled before wave 1

1. **Folder ownership.** Each widget lives in `Sources/OpenIslandApp/Nook/Widgets/<Name>/` and a builder edits only that folder. The registry files (`NookModel.swift`, `NookPanelView.swift`, `NookSettingsPane.swift`) already reference the names below and are owned by the boss.
2. **Service shape.** Every service is `@MainActor @Observable final class` with `func start(nook: NookModel)`, called once from `NookModel.start()`. Keep a `weak var nook: NookModel?` to call back into the model.
3. **Fixed names.** `NookCalendarService`, `NookCalendarCard`, `NookCalendarSettings`; `NookRemindersService`, `NookTodoCard`, `NookTodoSettings`; `NookNotesService`, `NookNotesCard`, `NookNotesSettings`; `NookTrayStore` (with `handleDrop(_:) -> Bool`), `NookTrayCard`, `NookTraySettings`; `NookFocusTimer` (with `closedText: String?`), `NookTimerCard`, `NookTimerSettings`; `NookMirrorCard`, `NookMirrorSettings`; `NookPowerMonitor`, `NookPowerSettings`.
4. **Cards.** `struct <Card>: View { var nook: NookModel; static let height: CGFloat }`. The height is the card's full rendered height including its own padding; the page frames the card to it. A builder may change its own height constant.
5. **Settings views.** `struct <Settings>: View { var nook: NookModel }` whose body is one or more `Section`s. They render inside a grouped `Form`.
6. **Closed notch.** Widgets never render on the closed island. They call `nook.showTransient(symbol:text:tint:duration:)` (SF Symbol name, short text, `Color`, `Duration`) or, for the timer, expose `closedText`. Text should fit in about 60pt: keep it under roughly 18 characters.
7. **Persistence.** Widget preferences go in `UserDefaults.standard` under keys prefixed `nook.<widget>.`. File-backed stores live under `~/Library/Application Support/OpenIsland/<Widget>/`. Notes go to the Obsidian vault file in the plan.
8. **Styling.** Reuse `NookCardBackground()` and `NookCardHeader(title:systemImage:trailing:)` from `NookPanelView.swift`. Dark surface, white text at 0.85 / 0.6 / 0.35 opacity. SF Symbols only.
9. **Check.** `swift build` from the repo root, zero errors.

## D10: Where parallel builders work
- Question: Builder worktrees pointed at the wrong repo; should builders share the main open-vibe-island checkout or get their own worktree?
- Ruling: One git worktree per builder, made from `~/code/open-vibe-island` on the current `nook` state, e.g. `~/code/open-vibe-island-wt/<widget>`. Before creating them the boss makes sure each worktree has the full current scaffold: if the Nook scaffold, PLAN.md and DECISIONS.md are uncommitted, the boss commits them on `nook` first (builders still never commit); if the boss will not commit, copy the working tree into the worktree with everything except `.build/` and `.git`. Each builder edits only its `Sources/OpenIslandApp/Nook/Widgets/<Name>/` inside its own worktree and runs `swift build` there. The canonical decisions log stays at `~/code/open-vibe-island/DECISIONS.md`; builders read rulings from that path, not their worktree copy. Integration: the boss copies each finished `Widgets/<Name>/` folder back into the main checkout and runs `swift build` there once. Do not run builders in the main checkout concurrently.
- Why: Folders are disjoint, but all widgets compile into one target, so in a shared checkout one builder's half-written file breaks every other builder's `swift build`, and SwiftPM serializes on the shared `.build` lock.
- Applies to: all wave builders (Calendar, Todo, Notes, Tray, Timer, Mirror, Power) and the boss's launch and integration steps.

## D12: Calendar styles contract (wave 2)
- Ruling: The calendar card has five looks, `NookCalendarStyle` (`strip`, `agenda`, `timeline`, `hero`, `month`), one file each under `Sources/OpenIslandApp/Nook/Widgets/Calendar/Styles/NookCalendar<Name>View.swift`. Each is `struct NookCalendar<Name>View: View { var nook: NookModel; static let height: CGFloat }`. `NookCalendarCard` already supplies the outer padding (14 horizontal, 12 vertical), the card background, the fixed frame of exactly `height` points, and the no-access state. A style view draws content only: no background, no outer padding, and it must fit inside `height - 24` points without clipping. A builder may change its own `height` constant.
- Data, all read through `nook` (never call EventKit directly from a view):
  - `nook.upcomingEvents: [NookCalendarEvent]`: the next 7 days, already filtered to this display's calendars.
  - `nook.calendarEvents(from:to:) -> [NookCalendarEvent]`: any range, same filter. Synchronous; call it for at most a 6 week span per render and never inside a per-cell loop (fetch once, group by day).
  - `nook.tasksDue(on: Date) -> [NookTodoItem]`: open tasks due that day.
  - `nook.nextEvent`, `nook.currentMeeting(now:)`.
  - `nook.calendar.addEvent(_ draft: NookEventDraft) throws(NookCalendarError)`; show `error.message` inline on failure.
  - `NookEventQuickAdd.parse(_:on:now:calendar:) -> NookEventDraft?` turns typed text into a draft.
  - `nook.startNote(for: event)` when an event row is tapped.
  - `NookCalendarEvent` has `id, title, start, end, isAllDay, calendarColor, location, calendarID, meetingURL`.
- Shared views in `NookCalendarShared.swift` (do not edit; reuse): `NookCalendarRow(event:now:showsWeekday:onTap:)` (includes the join button when the event has a `meetingURL`), `NookCalendarTaskRow(task:)`, plus `NookCardHeader` from `NookPanelView.swift`.
- Marks: events are round dots in `event.calendarColor`; tasks are small square outlines.
- Time: use `TimelineView(.periodic(from: .now, by: 30))` for anything that shows "now" or a countdown. Selection state (picked day, visible week or month) is `@State` inside the view and starts on today.
- Styling: rule 8 still applies. White text at 0.85 / 0.6 / 0.35, SF Symbols, `.buttonStyle(.plain)` buttons with a 22pt hit area, rounded rectangles of radius 7 to 10 for chips and day cells, today's day number in `.orange`. Strings in English for now.
- Why: one contract lets five builders work in parallel on files that never touch.
- Applies to: wave 2 builders (strip, timeline, hero, month, quick add, timer).

## D13: Task sources
- Ruling: The todo widget reads tasks through `NookTodoSource`. `NookModel.todo` (`NookTodoHub`) holds the choice (`nook.todo.source`, `reminders` by default) and the Notion service; `nook.todo.source(reminders: nook.reminders)` returns the selected source. Reminders stays on `nook.reminders`. Notion code lives in `Widgets/Todo/Notion/`, keeps its token in the Keychain, and does no Keychain, disk or network work unless Notion is selected. Anything else that needs tasks (for example `NookModel.tasksDue(on:)`) reads the selected source, never a specific one.
- Why: one place decides where tasks come from, which keeps the calendar's task marks in step with the todo card.
- Applies to: the todo widget and every reader of tasks.

## D14: Task notes
- Ruling: `NookTodoItem.notes` holds a task's notes. `NookTodoSource` exposes `canEditNotes`, `notesUnavailableReason` and `setNotes(_:for:)`. The todo card opens a notes page when a task's title is tapped; the circle still completes. Unsaved or failed text is kept in `NookTodoHub.noteDrafts` (memory only) and never dropped. For Notion, the notes column is auto-picked only when it is named Notes, Note, Description or Details; any other text column must be chosen in settings, because the first edit replaces the column's content. Writing notes replaces rich formatting in that column with plain text.
- Why: guessing a text column could overwrite unrelated data in a stranger's database.
- Applies to: the todo widget and both task sources.

## D15: Resizable widgets and edit mode (wave 3)
- Sizes: `NookWidgetSize` is small, medium or large (`Nook/NookWidgetLayout.swift`), and every widget supports all three. The page is a two column grid. Small fills one column, about 219pt wide on the MacBook notch and 239pt on external displays, and is exactly `NookWidgetLayout.smallHeight` (120) tall. Medium and large span the page, about 448pt and 488pt wide. Medium keeps today's layout and height. Each card's `static func height(for: NookWidgetSize)` gives its heights (calendar: `height(for:style:)`); small must return `NookWidgetLayout.smallHeight`, and a builder may change its own medium and large numbers.
- Cards read `@Environment(\.nookWidgetSize)` and switch layout on it. The grid frames them, never the card. Content must fit without clipping at every size at the notch width. Small layouts drop secondary controls instead of shrinking text under 10pt.
- Layout data lives in `NookDisplayPreferences` (`widgetOrder`, `widgetSizes`, `hiddenWidgets`, `placements(enabled:)`). Change it only through `NookModel`: `widgetPlacements(for:)`, `addableWidgets(for:)`, `moveWidget(_:to:for:)` (index among the visible widgets), `setWidgetSize(_:_:for:)`, `hideWidget(_:for:)`, `addWidget(_:at:for:)`. The island edits `nook.activeProfile()`. Pure helpers: `NookWidgetLayout.rows`, `rowHeight`, `contentHeight`, `columnWidth`, `moving`, `snappedSize(from:translation:)`.
- Edit mode is `nook.isEditingLayout`. While it is on, the island does not collapse when the pointer leaves, and closing the island turns it off. `NookPanelView.editingExtraHeight` is the height the edit controls add under the grid; window sizing adds it while editing.
- Interactions: right-click any card for Small, Medium, Large, Edit Widgets and Remove. A 0.4s long-press on a card also enters edit mode. In edit mode each card is outlined, its content stops taking clicks (a clear overlay takes the gestures), dragging the card body reorders with live reflow, dragging the bottom-right grip resizes through `snappedSize`, and S/M/L buttons plus a remove button sit on the card. A shelf under the grid lists `addableWidgets` as chips: click to add at the end, or drag onto the grid to insert there. A Done button ends edit mode.
- Drag uses SwiftUI `DragGesture` in a named coordinate space with each card's frame recorded. Never `.draggable`, `.dropDestination` or an NSDraggingSession, because the island is a non-activating panel. Hovering a dragged card over another card moves it to that card's index.
- `NookWidgetGrid` is generic over its tile view, which lets the Personalization editor draw the same grid with placeholder tiles at a smaller scale.
- Timer entry: `NookTimerEntry.parse(_:) -> TimeInterval?` reads a plain number as minutes ("25"), "h:mm" ("1:30" is 90 minutes), and unit forms such as "1h", "1h30", "1h30m", "45m", "90s", "2h 15m", ignoring case and spaces. Results outside 1 second to 24 hours are nil. While the timer is idle and the island panel is the key window, a digit typed while no text field is being edited starts the entry with that digit, through a local keyDown monitor that exists only while the timer card is on screen and never takes keys when another text view is first responder or another window is key. Clicking the big time also starts it. Return sets the preset and starts, Escape cancels, and invalid input turns red and stays.
- Strings stay English inside cards. Personalization strings go in all three Localizable files.
- Why: one grid rule and one set of mutations keep the island, the window height and the settings editor in step.
- Applies to: wave 3 and wave 4 builders.

## D16: Motion, island sizing and the status halo (waves 5 to 7)
- Plan: the "Motion and halo" section of PLAN.md. Names below already exist as stubs from wave 0; keep their signatures.
- Motion: every animation comes from `Motion` (`Sources/OpenIslandApp/Motion/Motion.swift`): `islandOpen`, `islandClose`, `islandPop`, `popDuration`, `islandResize`, `islandResizeSettle`, `openedSurfaceUnmountDelay`, `openedContentReveal`, `pageSwitch`, `hoverScale`, `morph`, `contentSwap`, `selection`, `hover`, `press`, `toggleEnable`, `reflow`, `lift`, `editToggle`, `Motion.Halo.*`, `slotSwap`. Use `withMotion(_:_:)` for model writes, `.motionAnimation(_:value:)` for implicit animations, `PressableButtonStyle` and `.hoverHighlight(cornerRadius:)` for controls. No new animation literals outside `Motion.swift`. Springs for anything interruptible, curves only for fades. Reduce Motion falls back through `Motion.resolved` and `Motion.transition`.
- Island sizing (approach B): the window grows before the shape and shrinks `Motion.islandResizeSettle` after it. `OverlayUICoordinator.openedLayout: IslandOpenedLayout` is the single source of the opened heights; it is published inside `withAnimation(Motion.islandResize)` when the island is open on the same screen, without animation otherwise, and before `notchStatus` changes on open. Refreshes coalesce to one per run-loop turn. Hit-testing follows the visible shape. `OverlayUICoordinator.closingPresentation` holds `appModel.liveOpenedPresentation()` taken at the start of `notchClose()` and is cleared on open; `notchOpenReason` still clears immediately. `AppModel.islandOpenedLayout` and `AppModel.openedPresentation` (live while open, snapshot otherwise) are what views read. Header height is `screen.islandClosedHeight` on both the window and view sides.
- Halo: `IslandHaloState.resolve(IslandHaloInputs)` is pure. Priority: style off gives `.off`; island opened shows only a flash (metrics `.opened`); approval orange breathing (`Motion.Halo.approvalPeriod`); question yellow breathing (`questionPeriod`); completed green flash (`flash`); notice tint steady; music tint drift (`driftPeriod`); running blue drift; idle `.off`. Metrics come from `IslandHaloMetrics` per style. Policy: `.reduced` turns breathing and drift into `.steady` and keeps the flash as one fade; `.conserving` (Low Power or thermal serious) also drops music and running; `.minimal` (thermal critical) shows only a steady waiting glow. `AppModel.islandHaloState` builds the inputs (wave 0, do not move). `IslandHaloController.noteCompletion()` already fires on eligible completions.
- Halo rendering: `View.islandHalo(_ state: IslandHaloState, cornerRadius: CGFloat) -> some View` draws a Core Animation glow behind the view, following a rounded rect of the view's bounds with that corner radius, inset 6pt and shifted down by `state.drop`, spreading `state.radius` into the window's transparent insets. It never takes hits, applying an equal state is a no-op (no animation restart), color and opacity changes start from what is on screen, and the layer stores `restOpacity` so harness screenshots show it. `View.islandHaloPreview(_ state: IslandHaloState, cornerRadius: CGFloat) -> some View` is the pure SwiftUI twin for Settings (ImageRenderer cannot draw AppKit views).
- Closed pill: `V6ClosedPill` gains `drawsBackground: Bool = true` and `isLive: Bool = true` (false pauses the visualizer, the GIF and the bars via `UnifiedBars.isPaused`), becomes Equatable, animates on a content key (not only widths), clips its content to its shape, and `V6Palette.surface(for: V6ClosedLayout) -> Color` gives the fill (black on MacBook, ink on external). `IslandPreviewPill` keeps its call shape; its `now` becomes optional.
- Settings components: `PersonalizationCard`, `MonoChip`, `PersonalizationSectionHeader`, `PersonalizationToggleRow` in `Views/Settings/PersonalizationComponents.swift`. The pane keeps `optionCard(selected:title:action:icon:)`, `monoChip(title:selected:action:)`, `sectionHeader(title:note:)`, `editingProfile`, `lang`, `model` and `sampleSideSlot` as internal names that forward to the components, and the Nook extension keeps `nookLeftSlotSection`, `nookRightSlotExtras`, `nookClosedSection`, `nookOpenedSection`, `nookHaloSection`, so the two wave 6 builders never break each other.
- Personalization strings for the halo (keys under `settings.appearance.nook.`): `halo.title` ("05 · Status glow"), `halo.note`, `halo.off`, `halo.subtle`, `halo.vivid`, `halo.music.title`, `halo.music.note`, `halo.reducedMotion`, `preview.done`, in en, zh-Hans and zh-Hant.
- Harness: `OPEN_ISLAND_HALO=approval|question|flash|running|notice:RRGGBB|music:RRGGBB|off` and `OPEN_ISLAND_MOTION_POLICY=full|reduced|conserving|minimal`; `OPEN_ISLAND_TRACE_OVERLAY=1` logs layout refreshes and frame changes.
- Why: one motion vocabulary, one height source and one halo resolver keep the island, the window and Settings moving together, and keep continuous effects in Core Animation where they cost the app almost nothing.
- Applies to: every builder in waves 5 to 7.

## D17: Personalization templates
- Ruling: `PersonalizationTemplate` (`Sources/OpenIslandApp/Personalization/PersonalizationTemplate.swift`) is a full Personalization setup for one display: `appearance` (`IslandAppearancePreferences`), `nook` (`NookDisplayPreferences`) and `widgets` (the Nook page, in order, with sizes). `PersonalizationTemplate.all` holds the five the tab lists: cockpit, nowPlaying, planner, focus, minimal.
- A template is a whole definition, not a patch. `applying(to:)` replaces every Nook choice except `hiddenCalendarIDs`; it puts the template's widgets first, hides every other widget on that display, and keeps the order and sizes of the widgets it leaves off the page.
- A template touches one display and nothing else. It never changes the other display, and it never switches a widget on or off in the Nook tab. A template widget that is off there stays off: its place on the page is kept, and the applied card names it as left out (`widgetsSwitchedOff(enabled:)`). An earlier design switched such widgets on and hid them on the other display; undoing that could not be made exact, which is why it was dropped.
- A display is "on" a template while `matches(appearance:nook:)` is true: every choice equals the template's and `placements(enabled: allCases)` equals `widgets`. Calendars and the order and sizes of off-page widgets are not compared. Any visible change ends the match, and no template is shown as applied.
- Adding a field to `NookDisplayPreferences` or `IslandAppearancePreferences`: set it in every template. If it holds something personal that a template must not reset (like the calendars), carry it over in `applying(to:)`, skip it in `matches` and keep it in `PersonalizationSetup.undoing`.
- Templates never place the mirror. A camera control is the user's to add.
- Rules are pure functions of `PersonalizationSetup` (one display's `appearance` and `nook`): `appliedTemplateID`, `applying(_:keeping:)`, `undoing(_:)`. `AppModel+Templates.swift` only copies the setup out of the models and back. Undo is `AppModel.templateUndo`, per display, in memory for the session: it holds the setup from before the first template in a run of templates, clicking the applied template again leaves it alone, and it is offered only while the display still sits on a template.
- UI: `TemplatesSection` (reads the model, owns the folded state in `@AppStorage`) wraps `TemplateGallery` (pure) in `Views/Settings/TemplatesSection.swift`, above the Notch part. The thumbnail is drawn from the template's own settings (`previewLeft`, `previewRight`, `widgets`, `previewGlow`). Strings are `settings.appearance.templates.<id>.title`, `.bestFor`, `.point1` to `.point3`, plus `title`, `note`, `applied`, `undo`, `show`, `hide`, `current`, `switchedOff`, in all three Localizable files.
- Why: one definition per template keeps the card, the thumbnail and what a click does from drifting apart, and keeping a template to one display makes undo exact.
- Applies to: anyone adding a template or a Personalization preference.

## D18: The mirror is on demand, with a ring light
- Ruling: the Mirror widget's tile (`NookMirrorCard`) is a switch and never the camera. Clicking it sets `NookModel.isMirrorOn`, and the live camera (`NookMirrorView`) then sits above the grid at the top of the Nook page. Opening the Nook does not start the camera by itself.
- While the mirror is on it holds the island open: `OverlayUICoordinator.shouldAutoCollapseOnMouseLeave` is false, the same way edit mode holds it. A mirror that vanished whenever the pointer drifted off would be useless.
- The mirror turns off, and the camera and the ring light with it, when: its tile or its close button is clicked, the island closes (`notchClose`), the page switches to agents (`showAgentsPage`), the Nook page goes away for any other reason such as a notification card (`NookPanelView.onDisappear`, which also folds the event editor and the grown calendar), a page loses the Mirror tile (`NookMirrorLayout.losesTile`, checked on every saved display change), or the Mirror widget is switched off in the Nook tab. `isMirrorOn` lives in memory only. Together these mean a later open, a hover, or a tile that is put back never starts the camera.
- Turning the mirror off calls `NookMirrorController.stopNow()`, which stops the camera at once. The view's attach and detach still start the session and cover rebuilds while the page reflows.
- A long press on the tile enters edit mode before the button lets go, which is why the tile's action does nothing while `isEditingLayout` is true.
- Ring light: the bulb on the mirror toggles `NookModel.isRingLightOn` (saved under `nook.mirror.ringLight`). The light shows only while the mirror is on. `NookRingLight` is a click-through window over the island's screen, one level under the island, asking to be left out of screen recordings and shares (`sharingType = .none`, which newer capture paths may not honor; not checked on a real recording), drawing a warm white band along the screen's edge (`NookRingLightLayout`: a tenth of the shorter side, between 64 and 140 points, with a rounded inner edge). `NookModel.presentRingLight` is a hook the app model installs; a bare `NookModel` lights nothing, which keeps tests from lighting a real screen. The app cannot raise display brightness without private API, and it does not try.
- Sizes: the tile is 120 (small), 90 (medium) or 110 (large) tall. The mirror shows the whole camera picture with nothing cropped: the preview layer fits and never fills, and the mirror's height is the picture's height at the page's width (`NookMirrorLayout.height(pageWidth:aspectRatio:)`, 259pt for a 16 by 9 camera on the 448pt notch page). `NookMirrorController.aspectRatio` is read from the camera's format once the session runs and resizes the island when it changes. `NookMirrorLayout.isShown(isOn:placements:)` says whether the mirror shows on a page, and `NookPageExtras.mirrorHeight` carries the height into `NookPanelView.preferredHeight(...extras:)` for the window-sizing math. `NookMirrorLayout` and `NookRingLightLayout` are plain enums on purpose: the sizing math and the tests call them off the main actor.
- The mirror sits outside the grid's scroll area and stays in view while the widgets scroll.
- Why: a widget that switched the camera on every time the Nook opened was more than anyone asked for when they only wanted the mirror now and then.
- Applies to: the mirror widget and anything that sizes the Nook page or decides when the island closes.

## D19: Preview stage
- Ruling: the preview stage draws a whole Personalization setup from values, never from the live island. Input is a `PersonalizationSetup`, the display profile and the enabled widgets, which lets the same stage show the setup being edited or a template that is not applied.
- Rules are pure and live in `Personalization/PreviewScene.swift`. `PreviewMoment` has eight cases: idle, working, approval, finished, music, notice, openAgents, openNook. `PreviewScene.resolve(_:setup:profile:policy:flashToken:)` gives the bars mode, the music or notice holding the closed island (nil when the setup keeps it out), the center label (external display only, in the live island's order), the `IslandHaloInputs` fed to the real `IslandHaloState.resolve`, the opened page, the two bars, and the caption keys. `PreviewStoryboard.steps` is the "See it in action" order with a time per step.
- Captions are sentence keys under `settings.appearance.stage.caption.`: what happened, then what this setup does about it. A setup that shows nothing at a step still gets the step, and the caption says that. `PreviewScene.allCaptionKeys` lists every key; a test checks that the list is exactly what setups can produce and that all three string tables have them.
- Drawing is in `Views/Settings/PreviewStage.swift` and `PreviewNookPage.swift`. The closed island is the real `IslandPreviewPill` with `islandHaloPreview`. The agents page is `SessionListPanelPreview` with the shared `SessionListPreviewSamples`, limited to three sessions. The Nook page is the setup's real grid (`NookWidgetLayout.rows`, `NookPanelView.cardHeight`) filled with `NookSampleCard`, a still sample of each widget at each size and calendar look. The real cards read live services, which is why samples are drawn. The stage takes no clicks and is tagged as a sample.
- The scene is laid out at the island's real size and drawn at `PreviewStageMetrics.scale`. `PreviewStageMetrics.areaHeight` gives one stage height per setup, which keeps the sheet still while the storyboard plays; a taller page scrolls inside. A test checks that both pages of every template fit without scrolling and that the height math equals what is drawn.
- Entry points: a "Preview" control under each template card's thumbnail (a sibling above the card button, which keeps a click from applying the template) and "See it in action" beside the closed preview. Both open `PreviewStageSheet`. The template sheet has "Use this template", hidden when the template is already applied.
- Adding a widget, size, calendar look or Personalization preference: give it a sample in `NookSampleCard` or a branch in `PreviewScene`, and a caption key when a setup can turn it off.
- Why: a template or a setting means little until you see it, and one stage drawn from values shows any setup without touching the user's own.
- Applies to: anyone adding a template, a widget or a Personalization preference.

## D20: Open trigger and file drags
- Ruling: `IslandOpenTrigger` (`Island/IslandOpenTrigger.swift`) is `hover` (default) or `click`, stored in UserDefaults under `app.islandOpenTrigger`, exposed as `AppModel.islandOpenTrigger` and chosen in Settings, General. Files dragged to the island open it in both modes.
- Pointer decisions are pure. `IslandPointerRules.hoverOpens(trigger:isSuppressed:)` gates hover-open. `IslandPointerRules.clickAction(_:)` turns an `IslandClickContext` into one `IslandClickAction`: `open`, `dismiss`, `holdForDecision`, `pin`, `closeFromNotch` or `none`. `OverlayPanelController.handleMouseDown` only gathers the facts and acts on the answer.
- Click mode: hovering the closed island does nothing. A click opens it with reason `.click`, which never collapses on pointer exit. It closes on a click outside or on a second click on the notch.
- Hover mode: a click anywhere inside a hover-opened island pins it (`pinHoverOpenedIsland`, reason becomes `.click`). The click is only observed and still reaches the control under it. Cards (`.notification`) and the boot animation keep their own rules.
- Notch toggle: a click on the notch of an island held open closes it. The hit area is `notchToggleRect`: the notch pulled in 6pt from the header lanes and no taller than the opened header, because on an external display the notch reaches below the header. After such a close, hover-open waits until the pointer has left the closed island once (`isHoverSuppressedUntilExit`). A pending decision with keep-open on blocks the toggle, as it blocks click-outside.
- File drags: mouse-moved events stop while a button is held, and a closed panel passes mouse events through, which left a dragged file with no way in. `NotchEventMonitors` now also watches `.leftMouseDragged` and `.leftMouseUp` (mouse monitors, no new permission). `IslandFileDragTracker` records the drag pasteboard's change count at mouse-down. A press counts as a file drag when that count has changed and the pasteboard's types include `public.file-url` or `NSFilenamesPboardType`. Only the count and the types are read, never the contents, and only while the pointer is over the island. A press that began on the open island is never a file coming in.
- Arrival (`IslandPointerRules.fileDragArrival`): closed with the tray on the page opens the island with reason `.hover` on the Nook page (`AppModel.notchOpen(reason:surface:page:)`). Open on the agents page turns to the Nook page. A notification card is never pushed aside. With no tray on the page the island stays closed and the panel takes mouse events only while the files are over the pill (`setClosedPanelDragReceptive`), going back to pass-through when the drag moves off or 0.3s after it ends.

The store shows "Added to tray" or "File not added" as a notice, and ignores files that already live in the tray folder.
- Why: one set of pure rules keeps hover, click and drag behavior testable without a mouse, and a tray that cannot be reached while the island is closed is not a feature.
- Applies to: anything that opens, closes or drops onto the island.

## D24: Links from other apps are a URL scheme
- Ruling: the scheme is `hangover://`. The release bundle (`scripts/package-app.sh`) registers only `hangover`. The dev bundle (`scripts/launch-dev-app.sh`) registers `hangover` and the upstream `openisland`. `IslandURLAction.parse` (`Island/IslandURLAction.swift`) reads both schemes (`IslandURLAction.acceptedSchemes`) under the same rules, is strict, and its cases are the whole list: `nook`, `agents`, `timer/start` (optional `minutes` from 1 to 1440), `timer/pomodoro`, `timer/stop`, `mirror/on|off|toggle`, `ringlight/on|off|toggle`.
- Not App Intents: the app is built by SwiftPM and bundled by script, which produces no `Metadata.appintents`, and Shortcuts would never list native actions. Shortcuts ("Open URL") and Raycast can both call the scheme.
- Nothing in a link is run, opened or passed along. Unknown words, extra parts, extra query items, userinfo, ports and fragments get the link ignored with a log line.
- A link never pushes a notification card aside, and a page link is also refused while an approval or a question is on screen in a row of the open list (`AppModel.showsWaitingRequestInList`, passed to `IslandURLPageMove.resolve`). Mirror on requires the Mirror tile and opens the island, which is also what shows the camera is on.
- A timer link holds agent completion cards the same way a timer started by hand does: while a countdown or a pomodoro work round runs and "hold completions during focus" is on, they do not pop.
- The boot animation opens only a closed island and closes only one that still carries the boot reason (`IslandBootAnimation`). A page link that turns a hover-opened or boot-opened island pins it open like a click (`IslandURLPageMove.pinsOnTurn`, `pinIslandOpenedForLink`), which keeps a link that launched the app from having its island, or the mirror, closed two seconds later.
- A link whose text is not a URL is logged and the keyboard is given back. Link text goes to the log through `IslandLinkLog.clean`, which strips control and formatting characters and cuts it short.
- The link is taken as an Apple event in `applicationWillFinishLaunching`, and the Settings scene handles no external events. After an action that shows nothing, `IslandFocusKeeper` returns the keyboard to the app the user was in, but only when the link was what brought this app forward.
- Any local app can call these, and a web page can after the browser's prompt. `AppModel.allowsLinksFromOtherApps` (Settings, General, "Allow links from other apps", on by default, saved under `app.allowsLinksFromOtherApps`) switches the whole scheme off: `handleIncomingURL` then ignores every link with a log line.
- Why: a fixed list of harmless actions gives Shortcuts, Raycast and scripts a way in without a second build system.
- Applies to: any new action reachable from outside the app. It must be a case in `IslandURLAction` with validated input.

## D25: Tray tools: sharing, clipboard history, quick actions
- Ruling: the tray card has two tabs in its header, Files and Clipboard. Clipboard history is part of the tray and is not a widget of its own.
- Sharing uses the system share picker hung off the file's tile (`NookTraySharing.swift`), plus a direct AirDrop action. While the picker is up, a click outside the island is the picker's (`IslandClickContext.hasOpenPicker`): the island neither closes nor reposts it, and the pointer leaving does not collapse it. A click on the notch still closes the island, and any press on the island ends the hold.
- Clipboard history is off until the user turns it on, in the card or in Settings. While off, nothing is read from the pasteboard, including the change count. Turning it off forgets every copy.
- It keeps the last 20 copies in memory only (`NookClipboardHistory`): text up to 256 KB, pictures up to 8 MB each and 24 MB together. Nothing is written to disk or logged. A repeated copy moves up and adds no row.
- A pasteboard carrying `org.nspasteboard.ConcealedType`, `TransientType` or `AutoGeneratedType` is never read. Copied files are skipped too.
- One poll a second reads the change count, then the types, then makes one read call (`NookClipboardMonitor`). The read is thrown away when the change count moved under it, because that copy was never checked for the private markers; the next poll picks it up. Text wins when a copy has both text and a picture. A picture is recorded first, after the size caps, and its thumbnail is drawn afterwards off the main actor (`NookClipboardHistory.setThumbnail`).
- macOS pasteboard privacy (15.4 and later): the history reads on `.default` and `.alwaysAllow`. On `.ask` it stops reading by itself, because every read would raise an alert, and offers Open Settings and a one-time "add current copy". On `.alwaysDeny` it reads nothing. Nothing is read at launch.
- Quick actions (`NookTrayFileActions.swift`) never change the file they start from. Zip uses `/usr/bin/ditto` without Mac-only extras, and a folder keeps its name as the top entry. Conversion uses ImageIO, turns the picture upright, drops camera data, and puts a white background under a see-through picture going to JPEG. A picture over 64 million pixels (`maxConvertPixels`) is refused from its header before anything is decoded, with its own notice. The result is a new tray item. A failure is logged: the zip tool's exit status in the public part of the line, its error output in the private part.
- Copy path copies the tray copy's path, because the tray does not record where a file came from.
- An action's result shows as a line in the card for three seconds. Failures also go to the closed island as a notice.
- Not built: sharing several files at once, pasting straight into the front app, pinned copies, rich text copies, promised files.
- Why: a tray that only holds files gave no reason to put them there. A clipboard history that starts on would record secrets from strangers who never asked for it.
- Applies to: the tray widget, and anything that reads the general pasteboard or opens a system picker from the island.

## D26: Scrub bar and speaker picker on now playing
- Ruling: the scrub bar seeks once, on release. A track with no length gets no bar.
- MediaRemote reports no "can seek" flag, which leaves `NookSeekTracker` to learn it. A seek is answered when the player lands within 3 seconds of the asked position, or when its clock jumps between two reports (`clockJumped`: more than 3 seconds from where the earlier report would have the track by now), or when a seek to the very end finds the track back at its start. A track whose clock carried on for 3 seconds as if nothing was asked is remembered (the newest 32) and gets a plain progress line. Any later jump of that track's clock forgets it, which covers a player that buffers past the window. A seek command that could not be started blames nothing. This is per track, not per app.
- The bar ticks once a second and not at all while paused.
- The speaker picker is drawn inside the card and is not a menu, because a menu opens outside the island and the pointer leaving the island closes it in hover mode. It lists CoreAudio outputs through the `NookAudioHardware` protocol, which tests replace with a fake, and follows devices coming and going.
- Alert sounds follow a switch only when they shared the old output.
- `AVRoutePickerView` was left out: it routes this app's own audio only. AirPlay targets appear only if CoreAudio lists them.
- The failed mark on an output is about one try. It clears when the picker opens (`beginPicking`), on a switch that works, and when the output list changes.
- `CoreAudioHardware` listens with `AudioObjectAddPropertyListener` and one C function plus one context pointer, never with blocks: CoreAudio matches a listener to remove by that pair, and a Swift closure handed over as a block is a new block each time. The context box holds the hardware weakly and is never freed.
- Why: a bar that looks draggable and does nothing reads as broken, and switching outputs is the other half of "what is playing".
- Applies to: the now playing card in all three sizes, and anything that reads or sets the sound output.

## D27: Volume notice and optional key takeover
- Ruling: a CoreAudio listener shows volume and mute changes in the closed pill with no permission. It is on by default and can be switched off.
- The first reading after launch, an output switch, and the 2 seconds after a switch are not announced. A key the app kept from macOS is the exception: it always shows the level as it stands (`NookVolumeNotice.content(for:)`), moved or not, settled or not, because Apple's popup is gone. `showTransient` gained `pops`, which lets a held key update the text without popping again.
- Taking over the volume and brightness keys is a separate switch, off by default, behind the Accessibility grant. It uses an event tap, which keeps the macOS popup away. The grant is requested once, from the switch, never at launch, and after that only checked every 2 seconds. A revoked grant removes the tap.

- Brightness uses private API: `DisplayServicesCanChangeBrightness`, `DisplayServicesGetBrightness` and `DisplayServicesSetBrightness`, soft-linked from `DisplayServices.framework`. Built-in display only, only with the takeover on, and the keys stay with macOS if any symbol is missing. There is no brightness notice without the takeover, because nothing public reports a brightness change.
- On a muted output the key sets mute first and the volume last. A refusal can then only come before the volume has moved, and macOS, which gets the key, moves it once.
- A key event that reaches the app more than 0.5 seconds after it was made stays with macOS (`NookMediaKeyRules.isStale`): macOS gave up waiting and handled it. The 2 second check also switches a tap back on that macOS switched off without a word (`NookMediaKeyFilter.revive`).
- Why: the notice costs no permission and can be on for everyone. Replacing a system popup needs a grant and private symbols, which a user must choose.
- Applies to: any new notice in the closed pill that repeats quickly, and any use of an event tap or a private framework.

## D28: Weather tile
- Ruling: a new widget kind, `weather`, off by default and in no template. Current conditions, high and low, and a forecast row: the next 5 hours (medium) or 7 (large), or a week of days. The small tile has neither.
- The medium and large tiles carry a two way switch in their header, hours or 7 day (`NookWeatherForecastMode`, saved under `nook.weather.forecastMode`). The week is today and the six days after it in the place's own calendar: weekday, sky, high and low, plus the day's top chance of rain in the large tile. It takes the hours' place at the same card height.
- The week comes in the same request as the rest, which asks for `forecast_days=7` with each day's weather code and `forecast_hours=48` from the current hour. Choosing a row never makes a request.
- A report saved before the week was kept has no sky for its days. It still loads, shows its hours, and offers no switch until the next report arrives, which can take up to 15 minutes.
- Data comes from Open-Meteo, which needs no key. Its free service is for non-commercial use, under 10,000 calls a day, 5,000 an hour and 600 a minute. Its data is CC BY 4.0, with a link required next to the data. The tile header carries an "Open-Meteo" link and Settings carries "Weather data by Open-Meteo.com". A paid release of the app would need their paid plan.
- The city is typed in Settings and geocoded by the same service, with no location permission. Coordinates go out rounded to two decimals. "Use my location" is not built.
- No request is made unless the widget is on. A report is requested when the tile is on screen or the city changes, at most every 15 minutes, with retries after 1, 2, 4 and 8 minutes, capped at 15.
- Reports are stored in Celsius in UserDefaults and shown in Fahrenheit by default, which makes the Celsius switch need no new request. A report keeps the place's time zone name, and the day's high and low follow that zone's calendar, which is right on the 23 and 25 hour days. A report saved without the name falls back to its fixed offset. A report shows its age from 30 minutes, and one older than an hour answers from its own hourly forecast. A failure shows a plain message, or the cached report.
- Was open, now done: `PRIVACY_POLICY.md` was rewritten for Hangover from the code. The line it replaced said the app sends nothing to external servers, while the weather tile and the Notion widget both do.
- Failures are sorted for the tile: no connection (`offline`), a service that could not be reached while online (`unreachable`: name lookup, secure connection, timeout), an error status, an answer that does not read. Logs carry the host, the error domain and code, and the path of a field that failed to read. They never carry a request URL or a value.
- The place search is asked in a two-letter language code, the only kind it knows. Both Chinese settings go out as `zh`, which returns simplified characters for both.
- Why: weather is the one glanceable thing the page lacked, and a typed city keeps it free of a location prompt.
- Applies to: the weather widget, and any new widget that makes a network request (off by default, no request while off, the source named in the tile).

## D29: Agent shortcuts, replies that keep, and the "what it did" card
- Ruling: two global shortcuts decide the waiting request: approve (default Control-Option-Y) and deny (default Control-Option-N). `AgentHotkeyController` (`AgentTools/AgentHotkeyController.swift`) owns the saved choices (`agentHotkeys.*` in UserDefaults), their state with macOS and when they are live. `CarbonHotkeyRegistrar` registers them as Carbon hot keys, which need no permission. The app hands the registrar over in `OpenIslandAppDelegate`, never in a harness run or a test.
- They are registered only while a press has a request to decide or show (`AppModel.refreshAgentHotkeyArming`, read from the same list a press decides from), and stay registered 2s after the last decision, which lets a key still held be seen as held. The rest of the time the keys belong to other apps.
- Which request: `AgentHotkeyRules.decision(in:)` is pure. A press decides a request only when that exact request, session and request id, is the island's single card, and only once 0.6s (`minimumVisibleTime`) have passed since it became that card and since the last decision. `AgentHotkeyController.noteShownCard` stamps the time when the card changes (`OverlayUICoordinator` reports its three open-state properties, `AppModel` every session change), never when the request arrived. A press is judged by when its key went down, read from the Carbon event.
- A request in the open list is never decided, in the top row or anywhere else: a row can be scrolled away or folded, and the list moves the next request up the moment one is decided. The press shows it as the card and decides nothing (`.reveal`). A card whose buttons are folded away is not decided. Its row reports the fold, the press opens it again, and opening restarts its time. A press approves once or denies. Always Allow has no shortcut.
- The approval card prints the keys under its buttons (`AgentHotkeyHintLine`), only on the card a press would decide and only for shortcuts macOS accepted. A row in the list never names them.
- No route, no keys: `AgentApprovalTracker` (`AppModel.agentApprovals`) notes where each waiting request came from. A request only the Codex app server reported, with no hook request for the session in the same wait, has no way back to the agent (`AgentApprovalRoute.agentOnly`). Its card says where to approve it and has no buttons, and the shortcuts ignore it and are not held for it.
- An approval or denial that never reaches the bridge is logged and shows a notice. When nothing else has happened to the session since, the request goes back to waiting, its card comes back and says the answer did not arrive (`agentApprovalWasNotDelivered`). A send the bridge accepts and cannot place is not caught.
- Key rules: a shortcut needs two modifiers with Control or Option among them, and the two keys may not be the same or touch on the keyboard (`AgentHotkeyKeyboard.areNeighbours`), whatever their modifiers. Settings, General, "Agent shortcuts" records a new one with a local key monitor, switches each off, and names a shortcut macOS refused (with its code) or uses itself (`CopySymbolicHotKeys`).
- Replies: `AgentReplyDraftStore` (`AppModel.agentReplies`) holds what is picked and typed on a question card, keyed by session and prompt, and the reply being typed to a finished session. The views read it through `AgentRowTools` bindings. A draft goes when its question is answered or replaced, when a finished session works again, or when the session goes. A reply field is emptied when the reply is handed over, which keeps a second Enter from sending it twice, and a reply that could not be sent goes back into it with a notice. Escape clears a reply field and gives the keyboard back. While a reply is being typed (`AppModel.isTypingAgentReply`) the island does not collapse on pointer exit or on the card timer. A click outside still closes it.
- `AgentQuestionReplyRoute` says whether an answer given in the island reaches the agent. Claude Code and its forks (held permission hook) and OpenCode (plugin) take one. Codex only reports that it waits, and `answerQuestion` for it changed local state and sent the text nowhere. Its card now says to answer in the terminal and has no field.
- What it did: `SessionActivityUpdated.startsTurn` (optional, absent in older events) marks the update that is a new prompt, set in every prompt hook and on Codex `turnStarted`. `SessionActivityUpdated.finishedTool` (optional) marks a tool call a hook saw end: Claude's and Codex's PostToolUse, with the file path or shell command taken whole from the hook payload. A denied tool gets no such hook, and a failed one gets PostToolUseFailure, which carries no marker. `AgentTurnLedger` (`AppModel.agentTurns`) is fed bridge events only and keeps, per session, the finished tool calls and permission requests since the last prompt. The "current tool" metadata is not counted: it names a tool being asked for.
- `AgentTurnSummary.make` gives no total of tool runs. Files come only from finished edit tools that named an absolute path, and the line is left off when one did not, when work went to a subagent (the bridge drops a subagent's hooks) or when calls were not kept. The count of commands is left off in those cases and when a command was started in the background. Test runs are finished shell commands that start a known runner (`AgentTestCommands`, which reads quotes, comments and here-documents through `AgentShellWords`, counts a runner after `&&` and not after `||`, and skips build-only and list flags). Claude Code and its forks get all of it. Codex gets commands and tests when its PostToolUse hook is installed. OpenCode, Pi, Cursor, Gemini and Grok get the time only. The permission count shows for Claude forks and OpenCode, whose requests reach the app once. It never says tests passed and never says none ran.
- Open: the bridge's approve command names a session, not a request, which leaves a few milliseconds where an answer meant for one request could land on a newer one from the same session. A failed send of a question's answer is still silent.
- It shows as one line in a finished row and as a line that unfolds on the completion card (`AgentTurnSummaryView`). `OverlayPanelController` adds the line's height to the row and card estimates.
- Why: a shortcut that can approve a command has to be unable to approve one the user has not seen, and a summary of an agent's work is only worth showing if every line of it is true.
- Applies to: anything that approves or denies for the user, any new reply field (drafts go in the store, typing reports through `onReplyEditingChanged`), any new hook integration (mark its prompt with `startsTurn` and a tool its hook saw end with `finishedTool`), and any new line on the card.

## D30: A request Claude Code wants approved in the terminal can only be denied from the island
- Ruling: Claude Code ignores a hook's approval for a call one of its `permissions.ask` rules matches, and honors a denial. The bridge reads those rules (`ClaudeAskRuleSource`) and marks a matching request with `PermissionRequest.requiresTerminalApproval`. The app gives it the route `AgentApprovalRoute.denyOnly`.
- The card for such a request says that Claude Code takes the approval in the terminal, and offers Deny and "Go to the terminal". Allow Once and Always Allow are not offered.
- An approval for it changes nothing and sends nothing: `AppModel.approvePermission` refuses it from every entry point, and the bridge holds one back and keeps the hook open, which keeps a denial possible.
- The approve shortcut never decides it (`AgentHotkeyRules.decision(for:in:)` answers `.needsTerminal`). It still shows the request as the card. The deny shortcut works under the usual rule, and the card names only that key. No notice is shown for the approve key, because notices live on the closed island and this card is open.
- Rules are read, never written, from the managed settings file and its `managed-settings.d` folder, the user settings file, and `.claude/settings.json` and `.claude/settings.local.json` of the hook's folder and each folder above it, up to and not counting the home folder or the root. A file that is missing, unreadable or not JSON gives no rules and a log line. A file is read again only when its date or size changes. A linked file is checked by the file it points to, no more than 4 MB is read, and the root folder is never a project.
- Matching (`ClaudeAskRuleMatcher`) covers a rule that names only a tool, `Bash(...)`, `Tool(param:value)`, `WebFetch(domain:...)` and `Agent(name)`. A Bash rule is tested against the whole command and each command inside it (`ClaudeBashCommandParts`), past leading assignments and the wrappers Claude Code strips. The command is read once per request, one Unicode scalar at a time, to 10,000 characters and 48 levels of nesting. Past either it is unreadable and counts as a match for any Bash rule, and the same goes for a command that opens with more than 64 words the reader would strip one at a time (`stripsTooManyWords`), because each strip copies the rest of the text.
- A paired phone or watch is sent the mark and offers only Deny. The relay refuses an approval of a marked request with a 409 and keeps the request waiting. It reads an answer as one of the request's two button titles or "allow" or "deny"; anything else decides nothing. Before, the phone's "allow once" was read as a denial. The phone and watch sources type check and were never built in Xcode or run on a device.
- A device only ever decides the request its card shows. The bridge keeps one waiting request per session, which means an answer acts on the session's newest: the relay retires a session's older ids when a new request arrives, when the session moves on, and when it finishes (`retirePendingRequests`). The two plain words are read before any button title.
- An answer for a session that no longer waits records nothing (`AppModel.isWaitingForApproval`), and an approval goes out only on the bridge route: a request with no route to its agent cannot be approved through the relay either.
- A question an ask rule matches is marked the same way (`QuestionPrompt.requiresTerminalAnswer`): the card says to answer in the terminal, and an answer from the island or a device is held back.
- A request whose hook connection closes is dropped and its card cleared. Whether Claude Code closes it when the user answers in the terminal is not confirmed; if it does not, the card stays until the tool finishes.
- Not built: the path patterns of `Read(...)` and `Edit(...)`, and `Skill(name)`. A rule of a kind that is not built matches nothing.
- Limits: rules handed to Claude Code on its command line with `--settings` cannot be seen, and neither can rules from a device policy, the claude.ai console, or a session on another machine. A rule the matcher misses leaves the old behavior, where the island sends an approval Claude Code ignores. The shell reading is a reading of text and errs toward matching, and walking up can read a file Claude Code did not load. A wrong match costs one approval made in the terminal.
- Only Claude Code is looked at. The agents that share its hook format keep their own settings.
- Found by: a live test on 2026-10-09. `launchctl version` against the rule `Bash(launchctl *)` could be denied from the island and not approved, while a file write outside the allowed folders was approved from it.
- Why: the island closed the card as approved while Claude Code went on waiting, which is worse than not offering the button.
- Applies to: every way an approval can leave the app, and any agent that is found to take only a denial from its hook.

## D31: Glow colors and the ring light tint
- Ruling: `IslandHaloPalette` (`Island/IslandHaloPalette.swift`) holds the halo's color for each moment: approval, question, completed, running, notice and music. `IslandHaloInputs.palette` carries it and `IslandHaloState.resolve` draws with it. `IslandHaloPalette.standard` is the old constants, and inputs that name no palette use it.
- A notice keeps the color it comes with while `palette.notice` is nil, and takes the palette's when it is set. Music takes the album art's color while `musicUsesArtwork` is on, and `palette.music` when the art has no clear color or the switch is off. With no color from either there is no music glow, as before. `IslandHaloInputs.isMusicPlaying` tells the resolver the music glow is wanted when the art gave nothing.
- One color for everything is literal: `IslandHaloColors.usesSingleColor` swaps in `IslandHaloPalette.single(_:)`, which colors notices and music too and does not read the album art. The palette under it is kept. "Glow with music" and "Timer and notices" still decide whether those two glow at all.
- Themes (`IslandHaloTheme.all`): the default plus ten from the design catalog. Picking one copies its palette. No theme id is saved; a display is on a theme while its palette equals the theme's. A theme sets a notice color and a music color, and the album art still wins while music plays. The catalog's color blind scores came from a simulation and were not tested with people: the app makes no claim about any theme, and the catalog's "Clear Sight" ships as "Daybreak".
- Saved per display with `haloStyle`, through the changed-keys path: `haloPalette` (a dictionary of "RRGGBB" strings and the artwork switch), `haloSingleColorOn`, `haloSingleColor`. A missing or damaged entry falls back per moment, and album art switched off with no music color saved gets the starter color (`suggestedMusic`), the one Settings shows. Switching album art off and on again leaves an untouched palette as it was (`IslandHaloPalette.setFollowsSource`). A picked color is rounded to eight bits a channel before it is kept (`IslandHaloRGB.quantized`).
- A template leaves `haloColors` alone when it is applied, matched and undone, the same as the hidden calendars.
- Settings: `GlowColorsSection` in "05 · Status glow" has the theme cards, the one color switch with ready swatches, a color well per moment, and the reset. Color wells write without animation because a drag writes many times a second: each step writes one key and asks for one coalesced layout refresh, and a change to the glow colors alone does not reset the page (`NookDisplayPreferences.changesThePage`). The stage and the real halo go through `resolve` with `effectivePalette`. The style cards draw one steady glow in a color from the palette, and the stage stands a sample color in for album art while album art is on.
- Ring light: `NookRingLightTint` (eight tints, warm white first and unchanged) is one choice for every display under `nook.mirror.ringLightTint`. The light reads it live. Every tint stays close to white, because the light is there to show a face.
- Harness: `OPEN_ISLAND_HALO_THEME=<theme id>` colors the forced states. The other `OPEN_ISLAND_HALO` values are unchanged.
- Not built: a warning for colors that are hard to see, the catalog's per-moment rhythms, sharing or importing a palette.
- Why: the glow is the most visible thing the app draws, and one fixed set of colors does not suit every wallpaper or every eye.
- Applies to: anything that draws a status color around the closed island, and any new halo moment, which needs a case in `IslandHaloMoment`, a palette entry and a color in every theme.

## D32: Frames and stickers on the mirror
- Ruling: the mirror carries one frame and up to 12 stickers (`NookMirrorDecorationSet`), saved under `nook.mirror.decorations`. `NookMirrorDecorationOverlay` draws them in a `Canvas` with no AppKit view and no clock, which lets the photo booth draw the same thing into a photo.
- Every design is drawn in code from the design catalog's recipes: no picture files. 16 frames and 30 stickers, each sticker in three colorways. The catalog was written from references read online, and nothing in it is copied artwork. A frame stays within 15 hundredths of the picture's height from an edge (`NookMirrorFrameDesigns.deepestReach`), and a test checks the middle stays clear.
- A sticker's place and width are fractions of the picture. Width runs from 0.07 to 0.34 of the picture's width. A sticker has a white rim and a shadow.
- The picker sits under the mirror, never over it, and adds its height through `NookPageExtras`. The mirror already holds the island open. The handles belong to `NookMirrorDecorationEditor` and never reach a photo.
- Saved data is sanitized on load: unknown designs are skipped, stickers are kept on the picture, and unreadable data means no decorations plus a log line.
- Words drawn on a frame or a sticker are artwork and are not translated. Lines thinner than 0.35pt are raised to it and words smaller than 3.5pt are left out, which keeps small drawings clean.
- Not built: blinking parts, an editable note on the Instant Print frame, layer order, a keyboard delete, face tracking. Every drag step saves to settings.
- Why: decorations are only worth having if a photo shows exactly what the mirror showed.
- Applies to: the mirror, the photo booth, and any new frame or sticker, which must be a design in `NookMirrorDesigns` with a name in three languages.

## D33: A photo booth in the mirror
- Ruling: a shutter button on the mirror runs a session (`Mirror/PhotoBooth/`): a countdown, four pictures from the mirror's own camera, then a strip drawn as a one-page PDF at real print size and saved at once.
- `NookPhotoBoothSession` is a plain state machine with the clock handed in. A picture is only asked for by the step after the last countdown number, and a step never ends early: a clock that jumps moves one step, never past a countdown.
- The pacing (one second to get ready, 5 before the first picture, 3 before the others, 1.2 to look, 0.8 to pose) is this app's choice, close to how event booths run, and not a measured standard. The first countdown is a setting: 3, 5 or 10.
- The booth has no camera of its own. `NookMirrorStillCamera` adds a still output to the mirror's session the first time it is used, through `NookMirrorController.onSessionQueue`. Turning the mirror off cancels the session (`NookModel.isMirrorOn`), which covers the x, closing the island, leaving the page and removing the tile.
- A session closes the sticker picker when it starts (`NookPhotoBoothModel.start`), and the booth's overlay takes clicks only while a strip or an error shows, which leaves the stickers under it draggable the rest of the time.
- Pictures are flipped to match the mirror and cut from the middle to the slot's shape. A sticker stays on the same spot of the camera's picture, one whose middle falls outside the cut is left off, and the frame is drawn again around the cut picture. The theme develops the camera's picture only; decorations keep their colors.
- `NookPhotoStripComposer` is a pure function from pictures, layout, theme, caption and date to PDF data. Three layouts and 16 themes. Page sizes are the ones booths print (2 by 6 and 6 by 4 inches); margins and slots are ours. Themes are drawn in code with fonts that ship with macOS, each with a system fallback.
- Strips go to `Pictures/Hangover Photo Booth` unless the user picks a folder. Apple's Mac Help names Desktop, Documents and Downloads as the folders macOS asks about, and Pictures is not one. A name is never reused. Retake moves the last strip to the Trash.
- The mirror goes off when the Mac sleeps, its screens sleep, the screen locks or another user takes over (`NookModel.screenWentAway`), which also ends a session. A countdown would otherwise pick up on wake and take its pictures behind the lock screen.
- A save that is cut short removes the part it wrote. Open: a failed save still throws the pictures away, and "Try again" shoots them again.
- Nothing leaves the Mac: a strip is a file in that folder, and Share and Add to tray act only on a press.
- Not built: starting the booth from a `hangover://` or `openisland://` link (another app must not be able to take pictures), uploading or sending photos anywhere, face tracking, Escape to cancel, a ring light flash, a strip with no caption line.
- Never run for real when this was written: adding the still output may change a camera's format, and the mirror reads its shape only once.
- Why: the mirror already had the camera, the decorations and the tray to hand the result to.
- Applies to: anything that takes a picture. It must start from a press on the mirror and show a countdown first.

## D34: The welcome tour
- Ruling: onboarding is a window of its own (`Onboarding/`), never the island. `OnboardingFlow` is a plain state machine over eight pages, and `OnboardingTour` joins it to a state closure and to `OnboardingActions`. - The tour says nothing is added to an agent's settings until the user clicks. Startup repair keeps that true: it re-runs an install only for an agent whose intent is `.installed` (`HookInstallationCoordinator.mayRepair`). Before, a missing OpenCode plugin was installed at launch for anyone with an OpenCode folder, chosen or not, and put back after it was removed.
- It shows by itself only on a fresh install (`OnboardingGate`): no launch was on record when this one began, the tour was never ended, and no harness is running. "On record" is the intent store's migration version, read before the startup migration writes it. An install that ran before never gets the tour by itself, hooks or no hooks. Known gap: an install older than the intent store, with no hooks, looks fresh once.
- Finishing, skipping and closing the window all set `firstLaunchCompleted` (`OnboardingTour.recording(in:)`). The tour is always in Settings, About.
- `AppModel.showOnboarding()` opens the tour on its agents page. The Setup tab is `showSetupSettings()`, one click away on that page.
- The tour asks macOS for nothing and has no action that could. Its only doors into the app are the nine closures in `OnboardingActions`, each run from a button: open trigger, connect an agent (the Setup tab's own install calls), all agents, widget switch, template, glow style, glow theme, opened width, opened corners. A failed connect says so on its row and points at Setup.
- The tour keeps its own picks (`OnboardingPicks`): a glow style picked in the tour is put back after a template, and the recap names the template that was picked. A template never touches the opened look or the glow theme.
- Any `OPEN_ISLAND_` name in the environment makes the launch a harness, which never gets the tour by itself.
- Every sentence on a page must be true of the code. The permissions page says what asks and when: camera on the first mirror, Accessibility from the volume key option and for Warp tab jumps, Calendar and Reminders the first time the calendar or the to-do tile is shown in an island the user opened, or when that widget is turned on in Settings, and never at launch, Automation as soon as an agent session is live, when the session monitor looks in Terminal or Ghostty for its window, and again for a terminal jump or a reply. - Not built: a practice request in the real notch, open at login, asking for a permission from inside the tour, Chinese snapshots.

A to-do widget on Notion never asks for Reminders. A permission that already has an answer is never asked for again. The tour's own widget switch asks for nothing. A model that was never started asks for nothing (`NookModel.allowsAccessRequests`), and each service takes its permission as a `NookEventKitAccess`, which tests replace.

- Applies to: any new page or claim in the tour, anything that changes when a permission is asked for, and any new first-run behavior.

## D35: The opened island's look
- Ruling: `IslandOpenedLook` holds a width (standard, wide, widest) and corners (soft, square), saved per display as `openedWidth` and `openedCorners` through the changed-keys path. `IslandOpenedMetrics.resolve` turns a look, a display kind and a screen width into every size, and nothing else may hold one.

## D36: Hangover updates itself from a feed of its own
- Ruling: from version 1.0.1 the packaged release starts Sparkle. It reads one feed, `appcast.xml` on the `main` branch of Hangover's own repository (`AppBrand.updateFeedURL`), once a day, and offers a newer version when the feed lists one. It installs nothing without the user's yes.
- Only a bundle that carries that exact feed address and Hangover's public key starts it (`UpdateChecker.shouldStart`). The release plist in `scripts/package-app.sh` carries both; the dev bundle and a test run carry neither. The delegate also pins the feed (`feedURLString(for:)`), which keeps a changed plist from pointing the updater anywhere else.
- The feed must never be the upstream project's. That feed lists Open Island and would replace this app with it. A test checks that every download in the feed is under Hangover's releases and is signed.
- Updates are signed with an EdDSA key made by `generate_keys --account hangover`. The private half lives in the owner's Keychain and is never in the repository. The public half is `AppBrand.updatePublicKey`. Losing the private half means installed copies accept no further update.
- Sparkle sends no system profile. The check is one request for the feed file, and the privacy policy says that.
- Limits: the release is ad-hoc signed and not notarized, which means macOS may ask for permissions again after an update. Version 1.0.0 has no updater. An app still running from the Downloads folder cannot replace itself; the README says to move it to Applications.
- Not verified when this was written: one version updating itself to the next on a real Mac.
- Why: without it every fix needs each user to find the releases page again.
- Applies to: anything that fetches or installs a new version, and any change to the feed, the key or the release plist.
